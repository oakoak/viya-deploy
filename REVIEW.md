# Ревью aml-deploy v0.1.1 — архитектура и код

Дата: 2026-10-01. Объём: `src/amldeploy` (~1650 строк), `bin/`, `config.schema.yaml`, `tests/unit`.
Не проверялось: реальный Viya (нет доступа), SAS-код, который читает `custom_config/current/...`.
Модель угроз: архив приносит свой человек, поэтому риски — ошибка, подмена по дороге, случайное имя ветки, а не внешний злоумышленник.

## Резюме

Архитектура здравая: один пакет на build/release/deploy с единой `FORMAT_VERSION`, атомарная замена симлинка `current`, идемпотентный reconcile job'ов и расписаний в Viya, audit-лог, офлайн-установка из `wheels/`.
Слабые места — безопасность распаковки/имён сборок, неатомарность и отсутствие отката при релизе, сетевой слой Viya без таймаутов/повторов, тесты.

## P0 — критично

**A1. Удаление произвольного каталога через имя сборки** (`release.py:107,120-124`).
`BUILD_NAME` берётся из `BUILD_INFO` внутри архива без проверки, затем `shutil.rmtree(build_root/BUILD_NAME)` и `move`.
Воспроизведено: архив с `BUILD_NAME=../../victim` стёр содержимое `victim/` вне `build/`.
Так же опасны `build -n ..` и `switch ../x` (`cli.py`, `build.py:52`, `release.py:58`).
Исправление: единая валидация имени (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) в build/switch/release и проверка, что target лежит внутри `build_root`.

**A2. Небезопасная распаковка** (`archive.py:117-125`).
Проверяется только `member.name`; симлинки, хардлинки и device-файлы в архиве не отсекаются, права и владелец переносятся. На сервере Python 3.8.8, `tarfile` filters недоступны.
Исправление: пропускать только обычные файлы и каталоги, запрещать абсолютные пути и `..`, сбрасывать uid/gid и setuid-биты, ручной `extractall(members=...)`.
Заодно `read_build_info_from_archive` берёт первый файл с basename `BUILD_INFO` в любом подкаталоге — нужен точный путь `<top>/BUILD_INFO`.

**A3. Перезапись активной сборки** (`release.py:113-125`).
Имя сборки = имя ветки, повторный релиз той же ветки делает `rmtree` активной сборки, затем `move`. Пока идёт копирование, `current` указывает на отсутствующий/неполный каталог, а SAS-job'ы в это время могут запускаться.
К тому же `tempfile.mkdtemp()` лежит в `/tmp`, `shutil.move` между файловыми системами копирует, а не переименовывает.
Исправление: распаковывать в `build/.incoming-<rand>` (та же ФС), затем `rename`; для активного имени — уникальный суффикс (commit/время) и swap симлинка.

**A4. TLS-проверка выключена** (`deploy.py:60`, `client.py:57`).
`verify=False` зашит по умолчанию и не настраивается из CLI/env, пароль уходит по непроверяемому каналу. Плюс глобальный `urllib3.disable_warnings` при импорте.
Исправление: `AML_DEPLOY_VIYA_CA_BUNDLE` / явный флаг `--insecure`, по умолчанию проверка включена.

**A5. Пароль без URL-кодирования** (`client.py:37`).
Payload собран через `str.format`: пароль с `&`, `+`, `%`, `=` ломает аутентификацию или подмешивает параметры.
Исправление: `data={"grant_type": ..., "username": ..., "password": ...}`.

## P1 — надёжность

**B1. Релиз не транзакционен относительно Viya** (`cli.py:95-99`). Симлинк переключается первым, затем Viya; при ошибке Viya файлы уже на новой сборке, Viya — частично обновлён, автоотката нет. Нет команды `rollback`. Активная сборка хранится в двух местах (`.current` и симлинк), `list` читает маркер, а не симлинк.
**B2. Нет блокировки.** Два одновременных release/deploy гонятся за `.current.new`, `rmtree` и Viya. Нужен `flock` на `custom_config/.aml-deploy.lock`.
**B3. Сетевой слой.** Запросы без `timeout` (возможно зависание), нет повторов на 5xx/429, токен не обновляется на 401. `ConnectionError`/`Timeout`/`KeyError` не ловятся в `deploy.py:109` (ловятся только `HTTPError`/`RuntimeError`) — прогон обрывается, отчёт пишется только в конце (`deploy.py:147`). Нужны `Retry`, `timeout`, `try/finally` вокруг отчёта.
**B4. `--dry-run` не dry.** В `release` он касается только шага Viya: распаковка и переключение выполняются. В `deploy.run` `ensure_folder_path` создаёт папки и в dry-run.
**B5. Инъекция в фильтры Viya** (`folders.py:19,28`, `job_definitions.py:9`, `job_requests.py:23,27`). Фильтры `eq(name,'{name}')` собираются форматированием; имя с `'` ломает запрос. Нужно экранирование и pattern на имена в схеме.
**B6. O(N²) обращений к Viya.** `find_managed_by_key` каждый раз скачивает все managed jobRequest (1–3 раза на job), `scheduler.find_all` на каждый модуль, `orphans.analyze` — ещё раз всё. Достаточно один раз загрузить и построить индексы.
**B7. Совместимость с SAS-потребителями (не проверено).** После перехода на единый `current` пути `custom_config/env` и `custom_config/jobs` больше не симлинки. Нужно убедиться, что `get_param.sh`, `m_load_env.sas`, autoexec и cron используют `custom_config/current/env`, иначе — compat-симлинки.
**B8. Целостность и воспроизводимость архива.** Нет checksum/подписи при переносе на сервер; mtime/uid в tar и заголовок gzip делают сборку одного коммита разной по байтам. Исправление: sha256 в `BUILD_INFO`/рядом и проверка в `release`, нормализация `TarInfo`, `+x` для `*.sh` выставлять при сборке.
**B9. Нет политики хранения.** `build/` копит все версии. Нужна `prune --keep N` (активную и предыдущую не трогать).

## P2 — улучшения

- **C1.** `job_definitions.create/update` шлют в API весь dict job (с ключом `schedule`) — whitelist по `CONTENT_KEYS`.
- **C2.** Логирование через `print`: нет уровней, времени, пользователя/хоста; audit-лог без ротации.
- **C3.** `--allow-delete` считает «лишним» всё, чего нет в конфиге по имени, включая вручную созданное; нужен diff + подтверждение; порядок «определения → jobRequest» оставляет битые ссылки до этапа orphans.
- **C4.** `DEFAULT_TIMEZONE="Europe/Moscow"` зашит в `scheduler.py`; `startDate` — локальная дата хоста.
- **C5.** Мелочи: `_find_repo_root` молча берёт cwd без `.git`; дубли `_prop`/`_get_property`, `parse_env`/`parse_build_info`; `a/b` и `a_b` дают одно имя сборки; `release.py:109` f-string без плейсхолдеров; в `pyproject.toml` и `requirements-dev.txt` устарели ссылки на `params.local.env`.
- **C6.** Секреты: `tests/aml-deploy.local.env` с реквизитами лежит в дереве; `.gitignore` внутри `deploy/` не виден (родитель репозитория не подключён) — проверить. При чтении `aml-deploy.env` проверять права (0600). Для `wheels/` — `pip --require-hashes`.
- **C7.** `config.yaml` (18 КБ) содержит SAS-код inline; рассмотреть `code_file:` для читаемых диффов.
